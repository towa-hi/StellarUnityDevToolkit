Stellar Dev Toolkit

Technical documentation for the Stellar Dev Toolkit, a Unity toolkit for Stellar and Soroban by Scrying Stone.

Unity 6000.0+ Soroban RPC WebGL / IL2CPP Testnet & Mainnet

This documentation covers building a Unity game that talks to Soroban smart contracts. It assumes you are comfortable in Unity and C#, and that you have a passing familiarity with Stellar: you know roughly what an account, a transaction and a smart contract are, but you have not wired one into a game loop before.

The chapters are ordered so that each one only depends on the ones before it. Chapters 1 to 4 get you from an empty project to a working contract call. Chapters 5 to 8 cover the four things you will actually spend your time on: moving data across the boundary, reading state, signing, and writing. Chapter 9 covers the patterns that matter once it all works.

Code blocks marked source are copied from the toolkit or its sample project. Blocks marked example are illustrative and are not code you will find in the repository.

Chapter 1Overview

The Stellar Dev Toolkit is a managed C# layer over the Soroban JSON-RPC API. It allows a Unity game to interact with Stellar smart contracts: building transactions, signing them, encoding them to the network's binary format, sending them to a Soroban node, and decoding what comes back.

The networking half of it is ordinary managed C# built on UnityWebRequest and Newtonsoft.Json — no native binary, no external process, and no separate runtime to ship alongside your game. (Browser wallet signing is the one exception, and it adds a small JavaScript bridge rather than anything native.) That matters more than it sounds: it is the reason the toolkit survives IL2CPP code stripping and runs inside a browser, which is where most Stellar games are actually played.

The two packages

The toolkit is split across two Unity packages, and you may only need the first one.

  • com.scryingstone.stellar-sdk — Everything to do with the network. Transaction building, the RPC client, the binary serialization layer, and the conversion between C# values and Soroban contract values. Namespace StellarSDK, with supporting types in Stellar and Stellar.RPC.
  • com.scryingstone.stellar-wallet — A single signing method: the Freighter browser wallet, for WebGL builds. Namespace StellarWallet.

The wallet package is optional and replaceable. It plugs into the SDK through one delegate, so if you later want to sign with a hardware wallet, a passkey, or a custodial service of your own, you write something matching that delegate's shape and the SDK never needs to know anything changed. If your game signs with a key it holds itself, you can skip the wallet package entirely.

Both packages require Unity 6000.0 or higher, and both declare exactly one dependency, Newtonsoft.Json, which the Package Manager resolves for you.

How it fits together

There are only three moving parts on the main path. Your game code calls StellarClient, which talks to a Soroban RPC node over HTTPS. When browser wallet signing is involved, a second short path appears alongside it.

StellarClient is a static class. There is no instance to create, nothing to initialize at startup, and no connection to keep alive. Every method takes its configuration as an argument, which is the subject of the next chapter but one.

Calls are ordinary async Task methods that you await. Unity returns the continuation to the main thread, so you can touch UI and GameObjects straight after an await without marshalling anything yourself.

Chapter 2Installation

The goal for this chapter is a project with the packages installed, compiling, and confirmed to be reaching the network.

Adding the packages

Install through the Unity Package Manager using a git URL. Both packages live in the same repository, so a ?path= query on the end of the URL selects which one you want.

Open Window → Package Manager, press +, choose Add package from git URL, and paste one of the following. Add them one at a time; the Package Manager only accepts a single URL per operation.

If your game holds its own signing key, or you are not targeting WebGL, install the SDK alone and leave the wallet package out.

Unity Asset Store

The SDK is also published free on the Asset Store as Stellar RPC and XDR Serialization Tools. Add it to your account and install it through Package Manager → My Assets. This route needs no git client and gives you a fixed, reviewed version rather than whatever is currently on the branch.

The Asset Store listing covers the SDK only, so a WebGL project that needs Freighter signing still installs the wallet package from its git URL.

Verifying the install

The SDK ships a small runnable sample. Select the package in the Package Manager, open the Samples tab, and import RPC Demo.

It is a single scene and script that call the read-only endpoints against testnet and report pass or fail on screen and in the console. Nothing about it needs an account, a key or a deployed contract, which makes it a clean first check: if it passes, your packages resolved correctly and your machine can reach a Soroban node. If it fails, you have a connectivity or install problem rather than a code problem, and you have learned that before writing anything.

Chapter 3Core concepts

Four things turn up in essentially every piece of code you will write against this toolkit. They are worth understanding before the first call rather than after.

NetworkContext

NetworkContext is a plain serializable struct holding everything the SDK needs to know in order to act: which node to talk to, who you are, how to sign, and which contract you are calling. Every StellarClient method that touches the network takes one as its first argument. (The pure helpers — address conversion, reading a result apart — do not need one, and neither does the testnet account helper, which has a fixed address of its own.)

This is why StellarClient can be static and stateless. There is no global configuration to set up and no risk of one part of your game reconfiguring the client out from under another. If you need to talk to two contracts, or to act as two different accounts, you hold two contexts.

The fields you will set on every context:

  • serverUri — the Soroban RPC endpoint. Every request is posted here.
  • userAccount — who the transaction comes from, and the identity that signs it.
  • signingMethod and unityWalletSigner — how signing happens, covered in Chapter 7.
  • contractAddress — the contract you are calling.
  • pollRateMs and maxAttempts — how patiently to wait for a submitted transaction to land. A thousand milliseconds and thirty attempts is a reasonable default.

The rest are situational. assetCode and assetIssuerAddress only matter for classic asset balances, and online and isTestnet are flags for your own code to branch on — the SDK stores them but never reads them.

Note

Because it is a struct, assigning a NetworkContext copies it. That is genuinely useful: to make one call against a different contract, copy the context, change contractAddress on the copy, and pass that. Your original is untouched, so there is no way to accidentally leave the game pointed at the wrong contract.

Result and StatusCode

Nothing in the SDK throws an exception for a failure you should have expected. Network errors, rejected transactions, contract panics and cancelled signatures all come back as values. Every method returns Result<T>.

The pattern is always the same: call, check IsError, and either read Value or report Message. Code is a StatusCode telling you what kind of failure it was, which matters because the right response differs a lot. A network error is worth retrying; a contract error never is.

The full enum is in the appendix. In practice you will branch on a handful:

CodeMeaning and what to do
SUCCESSIt worked. IsOk tests for this.
NETWORK_ERRORThe request never reached a node, or the node returned an HTTP error. Retrying is reasonable.
SIMULATION_FAILEDThe contract refused the call. Retrying will not help; the arguments or the state are wrong.
CONTRACT_ERRORAs above, but the contract raised a deliberate error rather than failing generically.
ENTRY_NOT_FOUNDYou read something that does not exist — usually an unfunded account or an empty storage slot. Frequently expected, so this one is logged as a warning rather than an error.
TRANSACTION_TIMEOUTYou stopped waiting. This does not mean the transaction failed. See Handling failure.
WALLET_SIGNING_CANCELLEDThe player dismissed the signing prompt. Normal behaviour, not an error condition.
Gotcha

Constructing a failed Result writes to the Unity console by itself. If you also log the message in your own handler, and the failure passes through a couple of wrapper methods on its way up, a single problem can produce four or five identical console entries. Log Message only at the point where you actually handle the failure.

Accounts and keys

MuxedAccount is the keypair type. It goes into NetworkContext.userAccount and identifies whoever the transaction is from.

ConstructorGives you
MuxedAccount.FromSecretSeed(seed)A full keypair from an S... secret seed. Can sign.
MuxedAccount.FromAccountId(address)A public identity from a G... address. Cannot sign — this is what you get from a browser wallet.
MuxedAccount.Random()A brand new keypair. Unfunded, so it does not exist on the network yet.
MuxedAccount.FromBIP39Seed(seed, index)Derived from a BIP-39 seed on the standard Stellar path. Note it takes the seed, not the mnemonic words — convert those yourself first.

The members you will reach for are AccountId, which is the G... string you show players, and CanSign(), which tells you whether this account has a private key behind it. Guard anything key-related on CanSign(), because a wallet-derived account will not have one.

On testnet, StellarClient.CreateAccount generates a keypair and asks Friendbot to fund it, which is the quickest way to get a usable account during development. It reports transport failures but does not verify that funding actually succeeded, so an unfunded account shows up later as ENTRY_NOT_FOUND the first time you read its state.

Tracking progress

Reads return in milliseconds, but writing to the ledger takes somewhere between five and fifteen seconds. That is long enough that a player will assume the game has frozen, so you need something on screen.

Every StellarClient method accepts an optional StellarClientTask as a trailing argument. Pass one in and it reports what the call is currently doing. Pass the same instance to every call and one object covers your whole game.

MemberUse
OnBusyChangedFires true when work starts and false when it finishes. This is the hook for showing and hiding a spinner.
IsBusyThe same state, polled instead of subscribed. Useful for disabling buttons.
CurrentStepA name for the stage in progress, such as simulating or submitting.
OnStepStarted, OnStepEndedFire as each stage begins and ends, if you want to narrate progress in more detail.

Chapter 4Your first round trip

This chapter goes end to end: a function and a type on a contract, a matching type in C#, and a call that sends data out and reads it back. It deliberately uses a read-only function, so nothing here needs a signature, a fee, or a wallet.

Getting a contract deployed

Writing and deploying Soroban contracts is documented thoroughly at developers.stellar.org, including installing Rust and the stellar CLI. There is no point repeating it here. The short version:

  • stellar contract init creates a Cargo workspace with your contract under contracts/.
  • stellar contract build compiles it to WebAssembly.
  • stellar contract deploy uploads it and prints a contract address beginning with C.

That address is the only thing that crosses from the Rust side to the Unity side. Everything else — the wasm, the build directory, the deployment state — stays on the contract side of the fence.

Gotcha

Build output lands in target/wasm32v1-none/release/. Older tutorials and scripts look for target/wasm32-unknown-unknown/release/ and will report that they cannot find your contract.

And echo_inventory takes no Address and touches no storage, so the network does not require anybody's authorization to run it. That is what lets this first call be free and immediate.

Worth doing

Put a handful of these in your own contract while you are building it out. When a call fails, the error rarely distinguishes between "your serialization is wrong" and "your contract logic is wrong". A few functions whose correct behaviour is obvious will tell you which of the two you are looking at, and that is worth the twenty lines.

The mirrored type in C#

You need a C# type of the same shape. The two are connected by nothing but field names, so those have to match the Rust names exactly.

Receiving a value needs nothing but the fields; the IScvMapCompatable interface and its ToScvMap method are only for sending one. Chapter 5 goes through the type mapping properly, but three rules are worth having now because each one fails quietly rather than loudly:

  • It must be a struct. Decoding into a class silently produces nothing.
  • Fields must be public and named exactly as in Rust. A name that does not match leaves that field at its default value rather than raising an error.
  • Sending a struct requires IScvMapCompatable. There is no generic handling for arbitrary structs on the way out.

Making the call

Build a context, build your argument, call the function, and read the result back into the mirrored type.

That is the shape of every contract call you will ever make with this toolkit. The rest of the document is variations on it. A few things to take away:

  • Function names are strings. Nothing generates bindings from your contract, so a typo in "echo_inventory" is a runtime failure rather than a compile error. Declaring them as constants in one place per contract is a cheap way to avoid that.
  • Arguments are an SCVal[], positional, in the order the contract declares them.
  • The result is nested, because a simulation reports on a whole transaction rather than a single function. Item2 is the simulation and the return value is the first entry in its Results list.
  • skipAccountEntry: true tells the SDK not to bother fetching your account first. A read does not need it, and skipping it removes a round trip — it also means this works with an account that has never been funded.

This was a simulation, which is free and instant but does not change anything. Writing to the ledger uses CallContractFunction instead, needs a signature, and takes several seconds. That is Chapter 8.

Chapter 5Contract data

Soroban contracts do not speak C#. Every value crossing the boundary becomes an SCVal, the network's own value type, and converting between that and your own types is the part of this work you will touch most often.

SCUtility handles it in both directions. Two methods cover nearly everything:

  • SCUtility.NativeToSCVal(value) converts a C# value into an SCVal to send.
  • SCUtility.SCValToNative<T>(scVal) converts a returned SCVal back into a C# value.

Type mapping

The primitives map about how you would expect. What matters is matching the widths: a Rust u32 and a C# uint are the same thing, but a C# int is not, and sending the wrong one produces a type error from the contract rather than a silent conversion.

Rust (contract)C#
u32uint
i32int
u64ulong
boolbool
Stringstring
Bytesbyte[]
Vec<T>T[]
Map<K, V>Dictionary<K, V>
#[contracttype] structA C# struct with matching public field names
AddressA string, converted with the address helpers below

C# enums are also supported and travel as u32, which pairs with a plain numeric value on the contract side. Vector2Int has built-in support and arrives as a struct with x and y fields, which is convenient for grid coordinates.

Structs and collections

Structs are where the sharp edges are, because a contract struct becomes a map keyed by field name and the matching is done by string comparison at runtime.

Receiving a struct needs nothing special. Declare a C# struct with public fields named the same as the contract's, and hand it to SCValToNative<T>. The sample project does exactly this to read a pair of arrays back from a contract:

Sending a struct requires you to implement IScvMapCompatable and build the map yourself, as shown in Chapter 4. There is no automatic handling for arbitrary structs on the way out, so a plain struct without the interface will fail at the point of conversion.

Gotcha

Three struct rules, all of which fail silently rather than loudly:

  • It must be a struct, not a class. A class produces an empty result.
  • Field names must match the contract exactly. A mismatched name leaves that field at its default, so a renamed contract field turns into a score of zero rather than an error.
  • When building a map to send, order the keys alphabetically. Soroban expects map keys sorted.

Types filled in by the conversion layer are invisible to Unity's code stripping, because nothing references their fields directly. The packages protect their own types, but yours are your responsibility: mark any struct you decode from a contract result with [UnityEngine.Scripting.Preserve]. This only bites in a stripped build, so a type that decodes perfectly in the Editor can come back empty in WebGL.

Chapter 6Reading from the network

Reads cost nothing, need no signature, and return in a single round trip. Anything you can answer with a read, you should — especially on a path that runs more than once.

Available endpoints

These are the informational endpoints, each a method on StellarClient taking your context and returning a Result.

MethodReturns
GetHealthAsyncWhether the node is healthy. Useful as a connectivity check.
GetLatestLedgerAsyncThe current ledger sequence number and protocol version. The cheapest possible "am I connected" call.
GetNetworkAsyncWhich network the node is on, including its passphrase. Worth checking against your own setting.
GetVersionInfoAsyncNode software versions.
GetFeeStatsAsyncRecent fee levels on the network.
GetLedgersAsyncA page of recent ledgers.
GetTransactionsAsyncA page of recent transactions.
GetEventsAsyncContract events in a ledger range, filtered by contract and topic. This is how you learn about things that happened without polling for them.
GetLedgerEntriesAsyncRaw ledger state by key. The foundation for the state reads below.

Reading a contract's return value is a different operation and is covered under contract storage and in Chapter 8.

Note

GetEventsAsync is the endpoint most worth knowing about, and the one most often overlooked. If your contract emits an event when something interesting happens, polling events over a ledger range is far cheaper than repeatedly asking the contract for its current state, and it gives you the history rather than just the present.

Interpreting results

The rule from Chapter 3 applies to every one of these: check IsError, then read Value.

Some responses carry data in the network's binary format rather than as plain JSON. Where that happens, the result object exposes a decoded property alongside the raw field, so you read the property and ignore the encoding entirely. Decoding is deferred until you first touch the property and then cached on the result object, so reading it repeatedly is cheap and you do not need to hoist it into a local yourself.

Gotcha

IsOk means the request completed, not that it returned what you expected. A node that rejects a malformed request can come back as a success with an empty payload. Check the fields you actually care about rather than treating IsOk as proof of a useful answer.

Account and asset state

There is no "get account" endpoint in Soroban RPC. Account state is ledger state, and you read it through a helper that wraps that up for you:

Because an account that has never been funded simply does not exist on the network, ENTRY_NOT_FOUND is the practical way to answer "is this account real yet". Balances are in stroops, a ten-millionth of an XLM each.

For classic (non-contract) assets, StellarClient.GetAssets reads the trustline holding that balance, using the assetCode and assetIssuerAddress on your context.

Reading contract storage

A contract's stored data is also ledger state, which means you can read it directly instead of invoking a getter. No fee, no signature, one round trip, and it works on data the contract exposes no function for.

StellarClient.MakeLedgerKey builds the key. You give it the name of the storage variant and the value identifying the entry — matching a Rust storage key such as DataKey::Owner(token_id):

Keys go to GetLedgerEntriesAsync as an array, so many entries resolve in one request. That batching is the whole reason to prefer this over a getter: fetching two hundred values costs one request rather than two hundred calls.

Trade-off

Reading storage directly couples your game to the contract's internal layout rather than its public interface. Rename a storage variant and the read breaks with nothing at compile time to warn you. It is the right call for state you poll often, and the wrong one for an occasional read where a simulated function call is clearer and safer.

Chapter 7Signing and WebGL

Everything so far has been read-only. Changing state needs a signature, and signing is the one part of the toolkit whose behaviour depends on your build target.

The two signing methods

The WebGL template

Browser wallet signing needs one piece of project setup that cannot be done from C#: a custom WebGL template that loads the Stellar JavaScript library into the page.

The wallet package loads the Freighter extension API itself, so that part needs nothing from you. What it cannot supply is the Stellar JS library, which it uses to check that the wallet's selected network matches the one your game asked for.

  1. Create the template folder Copy Unity's built-in Default WebGL template from your editor installation to Assets/WebGLTemplates/YourTemplate/. Starting from the built-in one keeps the placeholder macros Unity substitutes at build time.
  2. Add the Stellar JS library Put a built stellar-sdk.js in the template folder and reference it from the page head. This is the part that is genuinely required. The Freighter line on top is optional, since the package loads it anyway, but including it loads the extension API a little earlier and does no harm.
  3. Select it in Player Settings Player Settings → Resolution and Presentation → WebGL Template.
Gotcha

If the Stellar JS library is missing from the page, connecting fails even though the extension is installed, unlocked and working perfectly. The error points at the wallet, which sends you looking in the wrong place entirely. If connect fails and the extension looks fine, check the template first.

Player settings

WebGL builds have a few settings worth getting right before you start debugging symptoms.

SettingWhy it matters
Managed stripping levelHigher levels strip types that only the conversion layer touches. The packages protect their own; mark yours [Preserve].
Exception supportThe sample uses explicitly thrown exceptions only, which is faster but means null dereferences can fault the page instead of throwing something you can catch.
CompressionDisabled in the sample. Larger download, but it works on any static host without server configuration.
Memory sizeThe sample starts at 32 MB and grows to a 2 GB ceiling. Decoding network data allocates in bursts.

Checklist

Wallet signing does not work in the Editor, by design. With WebGL as your build target the Editor still takes the non-browser path, so CanFindWalletAsync() always reports false and signing requests fail immediately. Develop with PrivateKey and verify wallet signing in a real browser build.

  • Extension installed and unlocked.
  • The extension's selected network matches the isTestnet value you pass to ConnectWallet. A mismatch fails the connection.
  • Custom template selected, with stellar-sdk.js loaded.
  • Any type you decode from a contract result marked [Preserve].
  • The build served over http or https. Extensions do not inject into pages opened from disk, so a build opened as a local file will never find a wallet.
  • Network.UseTestNetwork() or UsePublicNetwork() called before the first signature.

Chapter 8Writing to the network

Writing is the one operation that costs money, takes seconds rather than milliseconds, and can fail after you have already committed to it. It deserves a little care.

Simulate or invoke

There are two ways to call a contract function and the difference is whether anything is recorded.

SimulateContractFunctionCallContractFunction
CostFreeFees
SignatureNoneRequired
EffectNothing is savedRecorded on the ledger
TimeMillisecondsTypically 5 to 15 seconds

Use simulation for every read. Calling a contract getter for real costs a fee, takes fifteen seconds, and returns exactly the same answer. Simulation is also how you find out what a write would cost before committing to it, since a simulated call reports the fee it would have charged.

The three results correspond to the three stages the call goes through, which is useful when something fails partway: the first tells you what the network expected to happen, the second that it was accepted for processing, and the third what actually happened.

What an invocation does

You do not need to drive any of this yourself, but knowing the shape of it explains most of the error messages you will see.

  1. Simulate The network works out what the call would touch and what it would cost. Soroban requires this; a transaction assembled without it gets rejected. A contract that refuses the call fails here, before anything is signed or paid for — which is why most contract errors arrive within a second.
  2. Assemble and sign The simulation's findings are folded into the transaction, and it is signed using whichever method your context specifies.
  3. Submit The transaction goes to the node, which accepts it into its queue. Acceptance is not success: it means the transaction is well-formed, not that it will do what you wanted.
  4. Wait The SDK polls until the ledger closes and the outcome is known, using the pollRateMs and maxAttempts on your context. At a thousand milliseconds and thirty attempts, the worst case is a thirty-second wait. Give the player something to look at, using a progress task.

Return values and fees

A contract's return value comes back in the transaction's metadata rather than alongside it, so retrieving it takes a couple of steps:

The same metadata carries the fee breakdown, via StellarClient.GetSorobanFees. Fees are in stroops and split into a non-refundable part, a refundable part, and rent for the storage the call touched. This is worth logging during development: it tells you which of your operations are expensive, and storage-heavy calls are usually the surprise.

Note

Read the return value rather than predicting it. If a contract mints something, or picks a number, or decides an outcome, the authoritative answer is in the result — not in a recalculation of the same logic in C#. Duplicating contract logic client-side to display an outcome works right up until the two disagree, and then it is a bug that only appears in production.

Handling failure

Writes fail in more ways than reads, and the distinctions matter:

  • SIMULATION_FAILED or CONTRACT_ERROR — the contract rejected the call and nothing was submitted or paid for. Retrying the same call will fail identically. The message is often terse; a failed simulation also carries diagnostic events from the contract, which is where the real reason tends to be.
  • WALLET_SIGNING_CANCELLED — the player declined. Not an error.
  • TRANSACTION_FAILED — it was submitted and the network rejected it. Rare, since simulation catches most problems first.
  • TRANSACTION_TIMEOUT — discussed below, and the one people get wrong.
Gotcha

TRANSACTION_TIMEOUT does not mean the transaction failed. It means you stopped waiting for it. It may well have been applied a second later. Treat it as an unknown outcome: keep the transaction hash from the result, and reconcile it later rather than assuming failure. Automatically retrying is how players end up paying twice for one thing.

Chapter 9Integration patterns

The mechanics are only half the problem. This chapter covers the design decisions that come up once calls are working, using the sample project as a worked example.

Submitting inputs, not outcomes

This is the most important idea in the document, and it is not about the toolkit at all.

A contract cannot trust anything your game tells it. A modified client can claim any score, any time, any outcome. If your contract records what the client reports, you have not built verification, you have built an honour system with fees attached.

The answer is to submit the inputs to a game and have the contract replay it. The sample does this for a puzzle game:

  • Each game gets a seed. Everything random derives from it, using the same algorithm on both sides, so the contract can regenerate the exact game the player was given.
  • Each move is recorded compactly — the sample packs one into a single byte.
  • On submission, the contract replays every move from the seed, recomputes the score, and rejects the submission if its own answer disagrees with the reported one, or if any move was illegal.

A whole game therefore travels as a seed and a handful of bytes, and the score is something the contract concluded rather than something it was told. The transferable rule: any number your contract records should be derivable from inputs the contract can re-execute. If it cannot be, it is a claim rather than a fact.

The cost is that the contract has to contain enough game logic to replay a game, and that logic has to match your C# exactly. That is a real constraint on design, and it is worth deciding early whether a given system needs this level of rigour. Cosmetic state usually does not. Anything attached to a reward does.

NFTs and SEP-50

SEP-50 is the Stellar standard for non-fungible tokens — ERC-721 in spirit, adapted to Soroban. It is still a draft, so treat the interface as stable in practice but not yet frozen.

The practical way to implement one is with the OpenZeppelin Stellar contracts rather than from scratch. Implementing their non-fungible trait gets you the core interface — ownership, balances, transfers, approvals and metadata — and you override only what is specific to your token. Enumeration, burning, royalties and batch minting are opt-in extensions on top, so if you need to list tokens on-chain, take the enumerable variant deliberately rather than expecting it by default.

On the Unity side the SDK includes ready-made helpers for the SEP-50 interface, so common operations do not need hand-built arguments. They read contractAddress from your context like anything else:

That last one deserves explanation, because "which tokens does this player own" is the question every game needs and the standard has no direct answer for. Asking the contract who owns each token in turn means one call per token. Instead, the helper reads the ownership records straight from contract storage in batches, using the technique from Chapter 6, then filters by address. It is the difference between two hundred requests and two.

Displaying artwork

Fetching a token's metadata URI is only the first step, and the toolkit stops there. The URI may point at an image or at a JSON document that in turn names one, and an ipfs:// URI has to be rewritten to an HTTP gateway before UnityWebRequest will fetch it. Plan on caching whatever you load; token artwork does not change, and a marketplace view that refetches on every open will feel slow.

Cross-contract calls

Contracts can call other contracts, and this turns out to be the cleanest way to handle rewards.

The problem: you want a player to receive an NFT for a qualifying score, but you cannot let players mint NFTs on demand. Minting has to be restricted to something trustworthy.

The solution is to make the game contract the authorized minter. The player signs one transaction submitting their game. The game contract validates it, and if the score qualifies, calls the NFT contract to mint. Because the NFT contract recognizes the game contract as its minter, the mint succeeds — even though the player could never have done it directly.

From Unity this is a single CallContractFunction. The mint is invisible in your C# — no second call, no second signature, no way for a player to get the reward without also submitting a valid game.

Two practical notes. On the contract side, calling another contract does not require depending on its code; you declare the functions you intend to call and Soroban generates a client from that declaration, which is why two contracts can be built against different SDK versions. And on the Unity side, a cross-contract call makes the transaction do more work, so expect a larger fee and a slightly longer wait than a plain write.

The sample project

The toolkit's sample project is a complete game wired to two deployed contracts, and it is the best reference for anything this documentation summarizes. It is worth reading in a specific order: the connection flow first, since that covers both signing methods and network selection; then a single gameplay submission, which is the whole write pipeline in context; then the asset views, which show reading and displaying token ownership.

It also contains a runnable test suite that exercises every endpoint and a long list of serialization round trips. If you are unsure how a particular type should cross the boundary, there is very likely already an example of it there, and copying that harness into your own project is a fast way to validate your own types.

Gotcha

The sample ships with a real testnet secret key in its settings asset, to save you creating an account before pressing play. It is a development convenience and nothing more. Do not carry that pattern into a real build, and never commit a key for a network where it controls anything of value.

Before shipping

  • No secret keys in the build. Player-owned assets mean wallet signing.
  • Contract addresses in configuration rather than source, because they change with every redeploy.
  • Every write shows progress, and blocks input while a signing prompt is open.
  • Cancelled signatures handled as a normal path, not an error.
  • Timeouts treated as an unknown outcome rather than a failure, with the transaction hash kept.
  • Reads and simulations on anything that happens often; writes reserved for moments that matter. The sample writes once per completed game, not once per move.
  • Outcomes read from contract results rather than predicted in C#.
  • Tested as an actual WebGL build, not only in the Editor. Stripping and wallet behaviour differ there and nowhere else.
