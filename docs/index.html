Stellar Dev Toolkit

Technical documentation for the Stellar Dev Toolkit, a Unity toolkit for Stellar and Soroban by Scrying Stone.

Unity 6000.0.28f1 stellar-sdk 0.1.0 stellar-wallet 0.1.0 soroban-sdk 22 / 25 Testnet

This documentation covers building an on-chain Unity game with the toolkit, from an empty project through to gameplay that writes to a Soroban contract. It assumes working knowledge of Unity and C#, and passing familiarity with Stellar concepts: accounts, transactions, and contracts.

Chapter 3 is intentionally brief. Contract authoring is covered properly by the official Stellar documentation and is not repeated here.

Code blocks marked source are copied from this repository. Blocks marked example are illustrative and are not present in the repository.

Chapter 1Components

The Stellar Dev Toolkit is a managed C# layer over the Soroban JSON-RPC API, distributed as two Unity packages. It allows a Unity game to interact with Stellar smart contracts: building transactions, signing them, encoding them to XDR, posting them to a Soroban node, and decoding the results.

The stack is UnityWebRequest, Newtonsoft.Json and hand-written XDR readers. No native plugin is required outside of WebGL wallet signing, which is why the toolkit survives IL2CPP stripping and runs in a browser.

Responsibilities are split between the two packages:

  • com.scryingstone.stellar-sdk: Transaction building, XDR, Soroban RPC, and SCVal serialization. Assembly StellarSDK.Runtime, namespace StellarSDK.
  • com.scryingstone.stellar-wallet: A signing method — Freighter browser wallet signing for WebGL builds. Assembly StellarSDK.Wallet.Runtime, namespace StellarWallet. It attaches to the SDK through a single signing delegate, and can be replaced with a custom signer — a hardware wallet, a passkey, a custodial service — without touching the SDK.

Both packages require Unity 6000.0 or higher. The only dependency is Newtonsoft.Json.

Chapter 2Installation

Target state for this chapter: a new Unity project with the packages installed, compiling, and ready to build.

  • Unity: 6000.0 minimum, declared in both package.json files. The sample project is authored in 6000.0.28f1.
  • Render pipeline: Irrelevant. The sample uses URP; nothing in the toolkit draws anything.
  • Dependencies: Newtonsoft.Json resolves transitively through the Package Manager. Do not add it manually.

Adding the packages

Install through the Package Manager with a git URL. Both packages live in one repository, so a ?path= query selects which one to install.

Window → Package Manager → + → Add package from git URL, then paste one of these. Add them one at a time.

Unity Asset Store

The SDK is also published free on the Asset Store as Stellar RPC and XDR Serialization Tools. Add it to the account, then install through Package Manager → My Assets. This route needs no git executable and gives a fixed, reviewed version.

The Asset Store carries the SDK only. A WebGL project that needs Freighter signing still takes the git URL for com.scryingstone.stellar-wallet.

Gotcha

StellarSDK.Runtime.asmdef sets overrideReferences: true and names four precompiled references: Newtonsoft.Json.dll, dotnetstandard-bip32.dll, dotnetstandard-bip39.dll and System.ComponentModel.Annotations.dll. The source additionally references Chaos.NaCl for Ed25519. In this checkout Runtime/Plugins/ contains only .meta files — the DLLs themselves are absent. They must be restored into Runtime/Plugins/ for the assembly to compile.

Verifying the install

The SDK ships a runnable sample. Select the package in the Package Manager, open the Samples tab and import RPC Demo.

It is a scene and one script that exercise the read-only endpoints — getHealth, getLatestLedger, getNetwork, getVersionInfo, getFeeStats, getLedgers, getTransactions and getEvents — against testnet, reporting pass or fail on screen and in the console. No account, keys or contract are needed, so it confirms the install and the network path in one step.

link.xml

Newtonsoft.Json reaches the RPC DTOs by reflection, which IL2CPP's managed stripping cannot see. Without preservation rules a WebGL build emits malformed JSON or throws inside the serializer, while the Editor works fine because Mono does not strip.

Chapter 3Contracts

Contract authoring is documented properly at developers.stellar.org, including toolchain installation, the Rust environment, and the stellar CLI. This chapter covers only what is needed to connect a contract to a Unity project.

Init, build, deploy

stellar contract init <dir> produces a Cargo workspace with contracts under contracts/*. Both workspaces in this repository follow that layout:

  • Contracts/unity-sample: the game contract. soroban-sdk 22.0.0, no other dependencies.
  • Contracts/nft: the NFT contract. soroban-sdk 25 plus OpenZeppelin Stellar crates pinned at =0.7.1.

Each crate declares crate-type = ["lib", "cdylib"] — cdylib for the deployable wasm, lib so tests and other crates can link it.

Gotcha

Build output lands in target/wasm32v1-none/release/, not target/wasm32-unknown-unknown/release/. Recent stellar contract build versions target wasm32v1-none. Deploy scripts copied from older tutorials will fail to find the artifact.

Deploy with stellar contract deploy, then paste the resulting C... address into NetworkContext.contractAddress. Both workspaces gitignore target, .soroban and .stellar, so no wasm and no deployment state is committed. The contract address is the only handoff artifact between the Rust and Unity sides.

Echo scaffolding

The sample contract carries roughly 30 trivial functions that exist purely to validate the C# side of serialization:

  • Primitives: echo_u32, echo_i32, echo_u64, echo_bool, echo_string, echo_bytes
  • Arithmetic: add_u32, add_i32, negate_i32
  • Collections: echo_vec, sum_vec, make_vec, echo_map, map_get, make_map
  • Structs: echo_inventory, make_inventory
  • Edge cases: echo_u32_zero, echo_empty_vec, echo_empty_string, echo_max_u32, echo_min_i32, echo_max_u64

This pattern is worth copying. SCVal conversion errors and genuine contract logic errors present identically from Unity — both arrive as a failed simulation. Having a set of functions whose correct behaviour is obvious separates the two failure modes before gameplay logic is in the way. Assets/Scripts/RpcTests.cs drives all of them.

Type matching

The SDK has no binding generator, so nothing verifies that the Rust and C# sides agree. Two places where they must:

  • Function names are passed as strings from C#. A typo is a runtime simulation failure, not a compile error.
  • Struct field names must match exactly. SCUtility maps a #[contracttype] struct to an SCVal map keyed by field name, and matches back onto public C# fields by name. Renaming a Rust field silently breaks decoding.
Note

The two workspaces here pin different SDK majors, 22.0.0 and 25. That is fine, because they never link against each other — cross-contract calls go through a declared trait rather than a crate dependency. See Cross-contract minting.

Signing is the only part of the toolkit that is platform-dependent. Local key signing works everywhere; browser wallet signing works only in a WebGL player build, and requires a WebGL template that the wallet package does not ship.

Note

WalletSigningCancelled is a normal outcome, not an error. Users dismiss signing popups routinely. It arrives from the jslib layer as code -9 and propagates to the SDK as WALLET_SIGNING_CANCELLED, which CallContractFunction forwards untouched. Treat it as "return to the previous screen", not as a failure to report.

Freighter loading

StellarClient.jspre injects the Freighter API itself, so the consuming project's template does not have to. It exposes the load promise as Module['StellarWalletFreighterReady'], which JSCheckWallet awaits before touching window.freighterApi.

It checks for window.freighterApi and for an existing script[data-stellar-freighter] tag first, so a template that also loads Freighter causes no double-load.

Gotcha

Freighter loads itself, but the Stellar JS SDK does not. JSGetFreighterAddress validates the connected network by reading Networks.TESTNET or Networks.PUBLIC off a global, and bails out with code -1 if no global is found:

The symptom is a connect that fails with the extension installed, unlocked and working. This is the reason the WebGL template below is mandatory.

WebGL template

A custom template is a folder under Assets/WebGLTemplates/ containing index.html and a TemplateData/ directory. Unity lists it in Player Settings once it exists; the sample's selection serializes as webGLTemplate: PROJECT:CustomTemplate.

  1. Create the folder Copy Unity's built-in Default template out of the editor installation to Assets/WebGLTemplates/CustomTemplate/. Starting from the built-in template keeps the {{{ LOADER_FILENAME }}}-style macros intact, which Unity substitutes at build time.
  2. Add the Stellar JS SDK Drop a built stellar-sdk.js into CustomTemplate/Scripts/ and reference it from the document head. This is the global the jslib needs.
  3. Add the head scripts
    • Line 9, Freighter from CDN: redundant with .jspre, and harmless — the .jspre detects it. Keeping it loads the extension API slightly earlier.
    • Line 10, stellar-sdk.js: required. Provides the Networks global.
    • Lines 11–16, stellar_xdr_json: optional. A wasm module exposing window.xdr for decoding XDR in the browser console. Useful for debugging envelopes; nothing in the C# path uses it.
  4. Leave the loader alone Nothing wallet-related hooks into createUnityInstance. The template's .then((unityInstance) => ...) block only wires the fullscreen and unload buttons. Because the bridge is callback-based, no reference to unityInstance is needed for signing.
  5. Select it Player Settings, Resolution and Presentation, WebGL Template.
Note

Assets/Plugins/WebGL/OpenLink.jslib is a much smaller second example of the same mechanism. It exports one function, JSOpenLinkInNewTab, used by LinkOpener.cs to open Stellar Expert transaction links — Application.OpenURL replaces the page in a WebGL build rather than opening a tab.

Testing

The wallet path is gated on #if UNITY_WEBGL && !UNITY_EDITOR. With WebGL as the active build target the Editor still takes the #else branch.

  • CanFindWalletAsync() returns false unconditionally in the Editor.
  • InvokeJs returns code -1 with "Wallet is only available in WebGL builds", which surfaces as WalletNotAvailable.

Develop against SigningMethod.PrivateKey and verify wallet signing in a real browser build. Serve the build over http or https — browser extensions do not inject into file:// pages, so window.freighterApi will never appear.

Checklist

  • Freighter extension installed and unlocked.
  • Freighter's selected network matches the isTestnet argument passed to ConnectWallet, or the address request fails with code -2.
  • stellar-sdk.js loaded by the template, exposing a Networks global.
  • Custom template selected in Player Settings.
  • link.xml present, covering both StellarSDK.Runtime and StellarSDK.Wallet.Runtime.
  • .jslib and .jspre import settings enabled for WebGL.
  • Build served over http or https, not opened from disk.
  • Network.UseTestNetwork() or UsePublicNetwork() called before the first signature.

Chapter 5RPC calls

Reads are cheap, unsigned, and instant compared to invocations. Anything that can be answered by an RPC read should be, especially on a hot path.

Transport

Every request in the SDK goes through one method. There is no connection pool, no retry, and no timeout beyond the platform default.

Serialization is Newtonsoft with a CamelCaseNamingStrategy contract resolver, which is why the C# DTOs use PascalCase properties and the wire format is camelCase.

Ledger keys

There is no getAccount method in Soroban RPC, and therefore none in the SDK. Account state is read by encoding a ledger key and passing it to getLedgerEntries:

An unfunded or nonexistent account returns zero entries, so ENTRY_NOT_FOUND is the practical "does this account exist" check.

The same mechanism reads contract storage directly, with no invocation, no signature and no fee. MakeLedgerKey builds the key for a contract storage entry:

The sym and key pair maps onto a Rust storage key of the form DataKey::Variant(value), which serializes as a two-element vector of a symbol and the payload. Encode the result with LedgerKeyXdr.EncodeToBase64 and pass it in GetLedgerEntriesParams.Keys.

getLedgerEntries takes an array, so many keys resolve in one request. The NFT owner map in Chapter 7 batches 200 at a time.

Note

Reading storage directly couples your client to the contract's internal storage layout rather than to its public interface. Renaming a DataKey variant breaks the read with no compile-time warning. It is the right trade for polling game state, and the wrong one for occasional reads where a simulation is clearer.

Lazy XDR decoding

RPC responses carry XDR as base64 strings. The generated DTOs hold the raw strings; hand-written partial classes add properties that decode on access.

TypeDecoded properties
EntriesLedgerKey, LedgerEntryData
ResultsResult (an SCVal), SorobanAuthorizations
GetTransactionResultTransactionResult, TransactionResultMeta, TransactionEnvelope, DiagnosticEventsXdr
SendTransactionResultErrorResult, DiagnosticEvents
SimulateTransactionResultSorobanTransactionData, DiagnosticEvents

Decoding is not free and not cached. Each access re-runs the XDR reader, so assign to a local rather than touching the property repeatedly in a loop.

Error handling

  • NETWORK_ERROR: transport failure, from ConnectionError or ProtocolError.
  • DESERIALIZATION_ERROR: the response body produced a null result.
  • ENTRY_NOT_FOUND: a ledger entry read returned the wrong number of entries. Logged as a warning rather than an error, since it is frequently expected.
Gotcha

SendJsonRequest never inspects the JSON-RPC error member. It reads .Result and only fails if that is null. A JsonRpcException type exists in JsonRpc.cs but is never thrown. A node-level error can therefore arrive as IsOk == true with a default-valued payload. Check the fields you care about, not just IsOk.

Assets/Scripts/RpcTests.cs is a working pass/fail harness covering every read endpoint plus contract round trips, and is worth copying into a new project as a connectivity check.

Chapter 6Simulation and invocation

Soroban requires simulation before submission. Simulation is what discovers the storage footprint, the resource fee, and the authorization entries a transaction needs; a transaction assembled without it will be rejected.

Entry points

SimulateContractFunctionCallContractFunction
CostFreeResource and inclusion fees
SignatureNoneRequired
StateRead-only, nothing committedCommitted to the ledger
DurationOne round trip5–15 seconds typical
Returns(Transaction, SimulateTransactionResult)(SimulateTransactionResult, SendTransactionResult, GetTransactionResult)

Use simulation for every read. A contract getter invoked for real costs money, takes fifteen seconds, and returns the same value.

Reading a simulated return value means reaching into the first result:

Invocation pipeline

CallContractFunction runs eight steps. Understanding them explains most failures.

  1. Simulate Calls SimulateContractFunction with skipAccountEntry: false, so the real account and sequence number are fetched first. BuildInvokeContractTransaction creates an InvokeHostFunction operation with a base fee of 100,000 stroops.
  2. Check the simulation A non-null sim.Error stops here. HasContractError scans the diagnostic events for an SCError.SceContract topic and picks CONTRACT_ERROR if found, SIMULATION_FAILED otherwise. A contract panic! surfaces at this step, not at submission.
  3. Double the resource fee long minResourceFee = long.Parse(sim.MinResourceFee) * 2; Ledger state can change between simulation and submission, which would make the simulated fee insufficient. Overpaying is safe — the unused refundable portion is returned.
  4. Assemble sim.ApplyTo(transaction) clones the transaction, adds the resource fee, writes the footprint into transaction.ext, and copies the authorization entries into the operation: It clones rather than mutating so that repeated simulations do not compound the fee.
  5. Sign Dispatches on signingMethod as described in Chapter 4. WALLET_SIGNING_CANCELLED is forwarded unchanged; every other signing failure becomes WALLET_ERROR.
  6. Submit sendTransaction. A non-null send.ErrorResult yields TRANSACTION_SEND_FAILED. Success here only means the node accepted the transaction into its queue, not that it succeeded.
  7. Poll WaitForGetTransactionResult waits pollRateMs, then calls getTransaction up to maxAttempts times. NOT_FOUND means keep waiting, FAILED yields TRANSACTION_FAILED, SUCCESS returns. Exhausting the attempts yields TRANSACTION_TIMEOUT. At the sample's 1000 ms and 30 attempts the worst case is a 30-second await.
  8. Return All three results are returned together, so fees, diagnostic events and the return value are all available.
Note

TRANSACTION_TIMEOUT does not mean the transaction failed. It means the client gave up waiting. The transaction may still be applied. Store the hash from SendTransactionResult.Hash and reconcile later rather than assuming failure and retrying, which risks double submission.

Struct decoding matches ScvMap keys to public fields by name. A mismatch leaves the field at its default rather than throwing, so a renamed Rust field shows up as a zero score rather than an error. Mirror the Rust type exactly:

The #pragma suppresses "field is never assigned", which is expected for a type only ever populated by reflection.

Other helpers: FromXdrString<T>(string) for base64 XDR straight to a native type, Get16ByteHash and HashEqual for comparing values, and SCVal.EncodeToBase64 / DecodeFromBase64 as the raw escape hatch. Every generated XDR type has a matching {Type}Xdr static class with the same pair.

Addresses

Two helpers, not interchangeable:

  • AccountStringToScvAddress(string): for G... account addresses. Decodes via StrKey.DecodeStellarAccountId.
  • ContractStringToScvAddress(string): for C... contract addresses. Decodes via StrKey.DecodeContractId.

Passing the wrong one throws inside StrKey during argument construction, before any network call. Validate user-entered addresses with StrKey.IsValidEd25519PublicKey and StrKey.IsValidContractId, as NetworkContextWindow does.

Gotchas

Gotcha

skipAccountEntry: true skips the ReqAccountEntry round trip and substitutes a placeholder account with sequence number 42069 and zero balance. Correct for pure reads — it halves the latency and works for an account that does not exist. Never use it for a transaction you intend to submit; the sequence number is wrong.

  • No binding generator. Function names are strings. Declare them once as const string on a static class per contract so a typo is a compile error in one place rather than a runtime failure everywhere.
  • RestorePreamble is inert. It is decoded on SimulateTransactionResult but CallContractFunction ignores it. If contract data has been archived, the invocation fails and the RestoreFootprint transaction must be built by hand.
  • Multi-party authorization is manual. GetAuthorisationsRequired(ledgerExpirationRelativeMax) and AddAuthorisationSignature(index, pubkey, sig) exist on SimulateTransactionResult but are not used by CallContractFunction, which only handles the source account's own authorization.
  • Diagnostic events are the real error message. When a simulation fails, sim.Error is often terse. sim.DiagnosticEvents carries the contract's own error topics and is where the actual cause appears.

Chapter 7NFTs

The sample's NFT is a SEP-50 non-fungible token built on the OpenZeppelin Stellar contracts. It represents a score reward in three tiers — 50, 100 and 500 points — and is minted by the game contract rather than by the player.

The contract

Contracts/nft uses four OpenZeppelin crates, all pinned to =0.7.1 on soroban-sdk 25:

  • stellar-tokens: Base, NonFungibleToken, and the enumerable module.
  • stellar-access: ownable, for owner storage and checks.
  • stellar-contract-utils: upgradeable.
  • stellar-macros: the #[only_owner] attribute.

Token-id encoding

The tier is packed into the token id rather than stored separately, which avoids a storage read per token:

With TOKEN_ID_STRIDE = 1000, the id is total_supply_before_mint * 1000 + points and the tier is token_id % 1000:

1st05050

Gotcha

Invalid points panic rather than returning a structured error: panic!("invalid asset points"). There is no #[contracterror] enum on this contract, so Unity sees CONTRACT_ERROR with no code to branch on. Validate the tier client-side before invoking — GameManager.MintSEP50AssetAsync rejects anything that is not 50, 100 or 500 before it reaches the network.

Finding owned tokens

There is no "tokens owned by address" query. The naive approach is total_supply, then owner_of for every id, which is N+1 simulations.

Chapter 8Gameplay integration

The sample game is a Block Blast clone: an 8×8 board, three offered polyomino shapes at a time, line clears with streak scoring, and a game over when nothing fits. It is a useful test case because the scoring is non-trivial enough that a contract cannot simply trust the client.

Determinism

The contract cannot accept a client-reported score. A modified client would report any number. The design response is to submit inputs, not outcomes, and have the contract replay the game.

Three pieces make the replay possible:

  • A shared seed. Each game gets one uint seed. Shape offers are generated from it by an xorshift32 RNG implemented identically in C# (IntegerRng) and Rust. Offer batches are a function of the seed and the move count.
  • A shared shape catalog. 6 trominoes and 19 tetrominoes, as packed 25-bit footprint masks over a 5×5 grid. Unity fetches them from the contract rather than hardcoding them, so the two sides cannot drift.
  • Packed moves. One byte per move, with an identical layout on both sides.

A full game is therefore a u64 seed plus one byte per move. On submission the contract replays it:

An illegal placement, a reused tray slot, or a score that does not match the recomputed total is rejected. Scoring is BASE_POINTS_PER_LINE = 10 with a streak bonus capped at MAX_STREAK_BONUS_PERCENT = 150, and the replay limit is MAX_REPLAY_MOVES = 10_000.

Note

This is the transferable lesson from the sample, independent of the game. Any score, time or outcome your contract records should be derivable from inputs the contract can re-execute. If it cannot, the number is a claim rather than a fact.

Production checklist

  • No secret seeds in shipped builds. Use SigningMethod.UnityWallet for anything public, and treat DefaultSettings.accountSecretSeed as development-only.
  • Contract addresses in configuration, not source. They change on every redeploy.
  • Every invocation has visible progress. Hook StellarClientTask.OnBusyChanged, and block input while WalletManager.IsWalletBusy is true.
  • WALLET_SIGNING_CANCELLED handled as a normal path, not an error dialog.
  • TRANSACTION_TIMEOUT handled as "unknown", not "failed". Keep the hash.
  • Simulations and ledger reads on hot paths; invocations only at meaningful boundaries. The sample writes once per game, not once per move.
  • Reward and outcome UI driven by the invocation result, not by a client-side prediction of what the contract did.
  • link.xml covering every assembly with reflection-deserialized types, verified in an actual WebGL build.
